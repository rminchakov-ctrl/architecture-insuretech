# Анализ текущих проблем
- **Синхронные и медленные вызовы:** Сервис ins-product-aggregator выполняет синхронные вызовы ко всем страховым компаниям по каждому запросу от core-app или ins-comp-settlement. Это создает высокую задержку и делает систему уязвимой к любым проблемам стороннего API.
- **Низкая доступность:** Если одна из пяти страховых компаний недоступна, весь агрегированный ответ может возвращаться без гарантии актуальности.
- **Неэффективное использование ресурсов:** core-app запрашивает данные каждые 15 минут, но при этом 99% этих запросов, весьма вероятно,  возвращают идентичные данные - информация о продуктах меняется нечасто. Это создает бесполезную нагрузку как на ins-product-aggregator, так и на API страховых компаний.
- **Проблемы с консистентностью:** core-app и ins-comp-settlement имеют свои собственные, независимо обновляемые копии данных. Между их обновлениями (15 мин vs 24 ч) существует окно, в котором их представления о продуктах могут расходиться, что может быть причиной наблюдаемых ошибок.
- **Немасштабируемость:** Добавление еще пяти компаний усугубит все вышеперечисленные проблемы. Время отклика может стать неприемлемым, а надежность системы еще больше снизится.

# Предложение по архитектурному решению
**Цель:** Перевести систему с синхронного взаимодействия на асинхронную модель на основе событий, чтобы обеспечить надежность, низкую задержку и легкую масштабируемость.

## Обновление ins-product-aggregator
Сервис должен стать единственным и авторитетным источником истины о страховых продуктах в системе.
- **Внутренняя база данных:** Сервис должен хранить последнюю известную согласованную версию всех продуктов и их тарифов от всех страховых компаний.
- **REST API для чтения:** Предоставляет синхронный API для сервисов (core-app, ins-comp-settlement) для мгновенного получения актуальных данных из своей локальной БД. Это быстрые и стабильные запросы, не зависящие от доступности внешних компаний.
- **Управляющий сервис:** Отвечает за координацию обновлений данных (через Kafka), валидацию и сохранение их в свою БД. Кроме того, может анализировать предложения от разных СК, выявляя более удачные предложения. Имея свою базу, делать это в асихронном рехиме - по расписаию, учитывающему стандартукю нагрузку.

## Реализация шлюзов (Insurance Gateway Adapters)
Для каждой страховой компании (и для новых партнеров) создается отдельный легковесный сервис-шлюз. Полная инкапсуляция сложности внешнего API, включая модель.
- **Единый контракт:** Все шлюзы реализуют одинаковый интерфейс взаимодействия.
- **Расписание:** Каждый шлюз работает по собственному расписанию, независимо опрашивает API своей страховой компании, результаты пишет в kafka (единый контракт).
- **Изоляция:** Проблемы API одной страховой компании не влияют на работу шлюзов других компаний и на основную систему.

## Внедрение Kafka как шины событий
Создаются топики Kafka для организации работы:
- **Топик для входящих данных:** insurance.product.update (ключ company_id).
- **Топик для исходящих событий:** product.aggregated.updates (опционально, см. ниже).

## Обновление сервисов-потребителей (core-app, ins-comp-settlement)
Отключают прямые вызовы к старому API ins-product-aggregator за агрегированными данными.
Поддерживают свои локальные реплики (кэши), которые обновляются либо по расписанию, либо по событию из Kafka, делая быстрый запрос к обновленному REST API ins-product-aggregator.

## Последовательность работы новой системы
- Шлюз страховой компании "Х" по расписанию запрашивает список продуктов через свой API.
- Шлюз преобразует ответ в стандартный формат и публикует его в топик insurance.product.update.
- ins-product-aggregator получает сообщение.
- ins-product-aggregator проверяет и валидирует данные, затем обновляет запись в своей БД.
- Опционально
-- После обновления БД, ins-product-aggregator может опубликовать событие в топик product.aggregated.updates о том, что появились новые актуальные данные.
-- core-app и ins-comp-settlement подписываются на топик product.aggregated.updates. Получив событие, они могут вызвать синхронный REST API ins-product-aggregator для немедленного обновления своих локальных кэшей. Альтернативно, они могут продолжать работать по расписанию, но теперь их запросы к ins-product-aggregator будут всегда быстрыми и надежными.

# Преимущества предложенного решения
- **Скорость:** Ответы ins-product-aggregator становятся мгновенными, так как данные всегда локальны.
- **Надежность:** Система устойчива к недоступности API страховых компаний. Потребители всегда получат данные, возможно, не самые свежие, но актуальные на момент последнего успешного обновления.
- **Масштабируемость:** Добавление новой страховой компании заключается лишь в создании для нее нового шлюза и подписке агрегатора на новый топик. Это не влияет на существующую систему.
- **Консистентность:** Все сервисы-потребители всегда получают данные из единого источника истины, что устраняет рассогласованность.
