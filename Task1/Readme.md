# Краткая оценка требований:
- Высокая доступность (99.9%): Требует устранения единых точек отказа на всех уровнях.
- Жёсткие RTO (45 мин) и RPO (15 мин): Требуют автоматического переключения (failover) с минимальными потерями данных.
- Географическое распределение и одинаковая скорость ответа: Требует развёртывания приложения в нескольких регионах РФ близко к пользователям. Для БД это означает необходимость репликации между центрами обработки данных (ЦОД).
- Объём данных (50 GB): Сравнительно маленький объём на текущий момент исключает необходимость шардирования данных для увеличения ёмкости.

# Детальное обоснование архитектуры
## Стратегия масштабирования и отказоустойчивости
Горизонтальное масштабирование. Это единственно верная стратегия для выполнения требований 24/7 и отказоустойчивости. Вертикальное масштабирование имеет предел и создаёт единую точку отказа. Мы будем масштабировать каждый уровень системы независимо:
- Приложение: Несколько подов сервиса внутри Kubernetes кластера региона + такие же кластеры в других регионах.
- База данных: Использование распределённой кластерной БД, которая реплицирует данные между узлами.
- Использование дополнительных зон безопасности (AZ) - обязательно. В рамках каждого региона приложение и БД должны быть развёрнуты как минимум в 2-3 разных разных дата-центрах.Это защитит от сбоя в одной зоне (отказ электропитания, сети и т.д.). На схеме для простоты каждая "нода" региона подразумевается развёрнутой в нескольких AZ.

## Конфигурация развёртывания в Kubernetes
Подход: Несколько независимых региональных кластеров.
Обоснование: Растянутый кластер Kubernetes хоть и возможен, но предъявляет жёсткие требования к сети между AZ (до 1-2 мс). Задержка между разными географическими регионами РФ (Москва-Новосибирск ~50мс) делает работу распределённого etcd и мастер-нод нестабильной. Гораздо надёжнее иметь независимые, самодостаточные кластеры в каждом регионе.

## Балансировка нагрузки
Уровень 1: Глобальная балансировка (Global Server Load Balancing - GSLB)
Принцип работы: Пользователь запрашивает app.example.com. DNS-сервер определяет его местоположение по IP и возвращает IP-адрес регионального балансировщика, находящегося к нему ближе всего.
Health Check: GeoDNS периодически опрашивает конечные точки региональных балансировщиков. Если весь регион становится недоступен, его запись DNS исключается из ответов, и трафик перенаправляется в ближайший рабочий регион.

Уровень 2: Региональная балансировка
Принцип работы: Распределяет входящий трафик внутри своего региона между подами приложения.
Health Check: Cloud LB и Ingress Controller постоянно опрашивают эндпоинт /health подов. Под, который не отвечает, исключается из пула балансировки.

## Фейловер-стратегия (Failover Strategy)
Уровень приложения: Описан выше через Health Check и GeoDNS. Клиент не видит падение региона, его просто незаметно перенаправляют в другой.
Уровень базы данных: Это самый критичный компонент. Стратегия должна обеспечить выполнение RPO=15 минут.
Сценарий 1: Падение Writer-ноды в основном регионе. Кластер БД автоматически назначает новую мастер-ноду (в том же или другом регионе, в зависимости от конфигурации), и приложение возобновляет работу с новым лидером.
Сценарий 2: Полное падение основного региона. Администратор (или автоматизированный скрипт) должен вручную инициировать перевод основного (мастер) статуса на кластер в резервном регионе. После этого GeoDNS переключает весь трафик на этот регион. Важно: требование RTO в 45 минут подразумевает, что этот процесс может быть ручным, но хорошо проработанным и отрепетированным. Для более жестких RTO потребуется полностью автоматическое решение, что сложнее и дороже.

## Конфигурация базы данных
Учитывая жёсткие требования к RPO (15 минут), необходим синхронный или полусинхронный механизм репликации.
Выбор технологии: Yandex Managed PostgreSQL или кластер Patroni для PostgreSQL.
Паттерн CQRS.
Схема репликации:
Регион 1 (Основной): Кластер БД из 3 нод в разных AZ. Одна нода — мастер, остальные — синхронные реплики на чтение.
Регион 2 (Резервный): Кластер из 2-3 нод, работающий в режиме синхронной реплики от Основного региона. Это гарантирует, что данные в этом регионе всегда консистентны, и при фейловере потери данных не произойдет (RPO ~ 0). Задержка между центральным регионом и резервным регионом обычно позволяет организовать синхронную репликацию.
Регион 3 (Дальний резерв): Кластер из 1-2 нод, работающий в режиме асинхронной реплики (от Основного или Резервного региона). Это нужно для географического резервирования данных на случай катастрофы в двух регионах сразу. RPO для этого региона может быть больше, но будет вписываться в общие 15 минут.
Для текущего сценария (стандартное приложение с сохранением в БД) введение асихнонных команд для записи не является обязательным и может излишне усложнить архитектуру. Требованиям RPO=15 и RTO=45 можно удовлетворить и без него.

## Шардирование БД
Решение: Не использовать на текущем этапе.
Обоснование: Текущий объём данных — 50 GB, что легко помещается на одну машину даже среднего класса. Шардирование значительно усложняет архитектуру. Шардирование применяют при исчерпании возможностей вертикального масштабирования одной машины (объёмы данных в сотни GB и TB) или для изоляции нагрузки. В данной задаче гораздо важнее обеспечить отказоустойчивость через репликацию, а не шардирование.
