# Анализ существующего REST API (Swagger контракта)
На основе предоставленного контракта можно выделить следующее:
## Ключевые ресурсы:
- Client (Клиент) — центральная сущность.
- Document (Документ) — дочерняя сущность по отношению к Client.
- Relative (Родственник) — дочерняя сущность по отношению к Client.

## Операции над ресурсами:
- GET /clients/{id} — Чтение основных атрибутов клиента.
- GET /clients/{id}/documents — Чтение коллекции документов клиента.
- GET /clients/{id}/relatives — Чтение коллекции родственников клиента.

## Проблемы текущего REST-подхода:
- Мультизапрос: Для получения полной информации о клиенте, его документах и родственниках клиенту (веб-приложению, мобильному app) необходимо сделать три последовательных запроса. Это создает избыточный сетевой трафик и увеличивает время загрузки.
- Избыточная выборка: Эндпоинты возвращают все поля ресурса. Невозможно запросить только имя и тип документа, не получив при этом все остальные поля (номер, даты).
- Недостаточная выборка: Часто клиенту нужны данные из нескольких ресурсов сразу (например, имя клиента и типы его документов), что требует нескольких запросов.
- Жесткость API: Структура ответа жестко задана на сервере. Клиент не может определить, какие данные ему нужны.

# Необходимые Запросы (Queries)
Все операции REST API покрываются единственной точкой входа — запросом client. Разница лишь в глубине и списке запрашиваемых полей.

## Эквивалент GET /clients/{id}:
``` graphql
query GetClientBasicInfo {
  client(id: "123") {
    id
    name
    age
  }
}
```

## Эквивалент GET /clients/{id}/documents:
``` graphql
query GetClientDocuments {
  client(id: "123") {
    documents {
      id
      type
      number
      issueDate
      expiryDate
    }
  }
}
```

## Эквивалент GET /clients/{id}/relatives:
``` graphql
query GetClientRelatives {
  client(id: "123") {
    relatives {
      id
      relationType
      name
      age
    }
  }
}
```

## Комплексный запрос (главное преимущество GraphQL):
``` graphql
query GetClientDashboardData {
  client(id: "123") {
    name
    documents {
      type
      number
    }
    relatives {
      relationType
      name
    }
  }
}
```
Этот один запрос заменяет собой три отдельных вызова в REST API.

# Анализ решения и преимущества GraphQL
GraphQL кардинально оптимизирует взаимодействие между потребителями (фронтендом) и сервисом client-info:
- Единый запрос вместо множественных: клиент может получить все необходимые данные для отрисовки целой страницы (например, профиля пользователя) за один сетевой запрос. Это значительно снижает задержку, особенно на мобильных устройствах с нестабильным соединением.
- Исключение Over-fetching: Клиентское приложение запрашивает только те поля, которые реально нужны для конкретного представления (View). Например, для dropdown со списком типов документов можно запросить только client { documents { type } }, не получая номера, даты и другие поля. Это экономит трафик и повышает эффективность.
- Мощный инструмент для агрегации данных: GraphQL-шлюз естественным образом становится единой точкой входа для клиентских приложений. В будущем его можно расширить, добавив данные из других сервисов, не меняя API для клиентов. BFF паттерн.
- Самодокументирующийся API: Схема GraphQL является строго типизированной и читаемой документацией. Такие инструменты, как GraphQL Playground или Apollo Studio, позволяют разработчикам изучать API и строить запросы интерактивно.
- Гибкость и эволюция API: Добавление новых полей и типов в схему не ломает существующие клиенты. Устаревшие поля можно помечать как @deprecated, а клиенты будут постепенно переходить на новые запросы.

Вывод: GraphQL не просто заменяет REST, он предоставляет качественно иной уровень контроля над данными для клиентских приложений, делая их более быстрыми и эффективными, уменьшает нагрузку на бэкенд за счет исключения лишней передачи данных.
