# Предложение по архитектурному решению
**Цель:** Добавить функциональность работы с ОСАГО предыдущему решению ins-product-aggregator:
- создать заявку на ОСАГО
- получить предложение по заявке
Решение создавать osago-aggregator считаю неверным, по следующим пунктам:
- нарушение DDD - ОСАГО не является уникальной бизнес-сущностью - это просто одна из типов страховок (а вот это уникальная бизнес-сущность)
- создавать сервис на каждый тип стаховок - накладное (и по ресурсам и по разработке) решение
- как было изложено в предыдущем архитектурном предложении: ins-product-aggregator - единый источник данных о страховках. Иначе, для агрегации данных о всех типах страховок клиента придется дописывать функционал агрегации в сервисе, в данном же решении все страховки клиента лежат в одной базе, управляются единым сервисом.

## Доработка API и взаимодействий core-app
**Цель:** Предоставить пользователю возможность отслеживать прогресс получения предложений в реальном времени.
REST API core-app для фронтенда:
- POST /api/osago/application: Создаёт заявку и немедленно возвращает её applicationId и URI для отслеживания.
- GET /api/osago/application/{id}: Возвращает текущий статус заявки и массив уже полученных предложений от СК. Для реализации реального времени на фронтенде используется Server-Sent Events (SSE) или WebSockets.

Интеграция core-app: фронтенд: WebSocket или Server-Sent Events (SSE).
Причина: REST не подходит для проталкивания обновлений. Как только core-app получает новое предложение от агрегатора, он должен немедленно уведомить подключённый фронтенд.
Реализация: После создания заявки фронтенд открывает WS/SSE соединение к core-app. core-app отправляет событие по этому соединению каждое раз, когда обновляется состояние заявки.

## Доработка интеграции core-app -> ins-product-aggregator
**Цель:** Надежно передать заявку на обработку и получать уведомления о новых предложениях.
Интеграция: Асинхронная (Kafka) + Синхронная (REST).
Синхронный вызов (core-app -> ins-product-aggregator):
- POST /api/osago/application: core-app синхронно вызывает этот метод у агрегатора, передавая данные заявки.
- Паттерны отказоустойчивости (здесь обязательно):
- - Retry (с экспоненциальным бэкоффом): на случай временной недоступности агрегатора.
- - Circuit Breaker: чтобы не завалить агрегатор, если он начал отвечать ошибками.
- - Timeout: должен быть небольшим (например, 1-2 секунды). Задача этого вызова — просто принять заявку в работу.
- Асинхронное уведомление (ins-product-aggregator -> core-app):
- Топик Kafka: osago.quotation.progress
- Агрегатор публикует в этот топик событие каждый раз, когда от всех СК приходит ответ (или таймаут). Событие содержит applicationId и данные предложения.
- core-app подписан на этот топик, обновляет состояние заявки и через WS/SSE отправляет обновление на фронтенд.

## Доработки ins-product-aggregator
**Цель:** Координировать запросы ко всем шлюзам, управлять таймаутами и агрегировать результаты.
- добавляем топик, в который приходят заявки на оформление ОСАГО от core-api.
- ins-product-aggregator прослушивает этот топик, по получению ставит всем шлюзам задачу на запрос заявки, тут возможны варианты: 
- - можно сделать в цикле по всем СК создать потоки и ждать - либо митуту, либо ответ
- - можно создать еще один топик, куда писать запрос к шлюзу
- шлюз либо делает запрос (ТА конфигурируется, в данном случае 59с), либо отвечает, что данная страховая не поддерживает ОСАГО
Внутренняя логика обработки заявки:
- Получает заявку от core-app (через REST API).
- Сохраняет её в свою БД со статусом IN_PROGRESS.
- Параллельно отправляет команду всем шлюзам (адаптерам) СК. 
- - Используется отдельный топик Kafka: osago.quotation.request.
- - Либо - цикл с потоками.
- Запускает таймер (60 секунд) на всю обработку этой заявки.
- Собирает ответы из топика osago.quotation.response.
- Как только пришли все ответы или истекло время, публикует финальное событие в osago.quotation.progress и обновляет статус заявки в БД.

### Вопросы к реализации
Необходимо рассчитать что выгоднее в данном решении: запрашивать шлюзы через kafka или в потоках.
Параметры:
- нагрузка на kafka
- навыки команды разработки

## Доработки шлюзов (Gateway Adapters)
**Цель:** Выполнить запрос к своей СК и вернуть результат, обеспечивая стабильность.
- Первым делом обновляем общий контракт - добаялем метод заявки на ОСАГО.
- Подписан на топик osago.quotation.request.
- Получив команду, немедленно выполняет синхронный вызов к API своей СК.
- Публикует результат (успех или ошибку/таймаут) в топик osago.quotation.response.
Паттерны отказоустойчивости для вызова к СК (критически важны):
- Timeout: ~55 секунд. Должен быть меньше общего таймаута агрегатора (60с), чтобы успеть обработать и отправить ответ.
- Retry: В зависимости от попадания в ТА.
- Circuit Breaker: Под вопросом. Если СК часто не отвечает или возвращает ошибки - поднимаем алерт, сообщаем поставщику, принимаем решение о потенциальном отключении поставщика.

# Применение паттернов отказоустойчивости (итог)
|Компонент|Назначение|Паттерн|
|--|--|--|
|**Frontend -> core-app**|Получение уведомлений о новых предложениях|-|
|**core-app -> aggregator**|Передача заявки на обработку|Retry, Circuit Breaker, Timeout|
|**aggregator -> шлюзы**|Рассылка команды на запрос предложения|- (считаем, что Kafka гарантирует доставку)|
|**Шлюзы -> СК**|Запрос предложения по ОСАГО|Timeout, Retry(?), Circuit Breaker(?)|
|**Шлюзы -> aggregator**|Возврат результата|- (считаем, что Kafka гарантирует доставку)|
|**aggregator -> core-app**|Уведомление о новом предложении|- (считаем, что Kafka гарантирует доставку)|

# Масштабируемость
Решение не зависит от количества экземпляров сервисов, а полностью полагается на Kafka как на центральный координатор.
- Шлюзы: Можно запускать множество экземпляров каждого шлюза. Kafka будет балансировать нагрузку между ними.
- ins-product-aggregator: Можно запускать несколько экземпляров. Они будут делить между собой работу через партиции топика osago.quotation.request.
- core-app: WebSocket/SSE соединения балансируются на уровне L4/L7 (например, с помощью sticky sessions в балансировщике нагрузки).
